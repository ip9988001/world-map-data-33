# 新增环节 07 / 08 / 09 —— 方案（待确认）

> 目标：**不改动 01~06 任何一个环节**。新口径、新产物、新 tag，另开一条流水线。
> 01~06 的验收快照保持可复算；新环节失败/重跑都不影响历史账本。

## 0. 为什么是"新增"而不是"改原环节"

| | 改原环节 | 新增环节 |
|---|---|---|
| 历史验收 | 不可复算（账本写 done，重跑对不上） | 原样保留，可随时复算 |
| 数据溯源 | 分不清哪批数据是哪版规则采的 | tag / 判据卡 / 账本各自独立 |
| 对比 | 口径变了就没法比 | 05 采的 与 07 采的 可以互相对账 |
| 成本 | 便宜（改数字） | 略贵（多 5 个文件），但框架是参数驱动的，代码几乎不用动 |

**结论：新增。** 同一个源 → 不同环节 = 不同采集规则 = 不同数据切面，这才是可长期维护的形态。

## 1. STEP 07 —— 扩口径补齐（采集）

**要解决什么**：05 排掉了"标题里带 fire / parcel / school / zone 等词"的层，但其中有真地址层被误伤（如 `X County Address Points for School District`）。

**口径**

```json
"select": {
  "mode": "bulk", "batch": 100, "order": "rows_desc",
  "rows_min": 5000, "rows_max": 5000000,
  "skip_blocked": true,
  "state_exclude": ["未定位", ""],
  "title_include": "address|addr\\b|situs|e-?911|ng911|mailing|delivery point|location point",
  "title_exclude": "europe|canada|mexico|fire response|nfirs|bus stop|billboard|licen|inspection|vacant|demolition",
  "exclude_done_tags": "collect-step02-,collect-step03-,collect-step04-,collect-step05-"
}
```

**体量**：980 层 / **1.33 亿行** / 预计 **1,281 job-分钟**
**预算**：剩余 964 分钟 → 一轮跑不完，**按 100 层/批推进，跑满预算停手**，预计可完成约 730~780 层，剩余进下一轮。

**产物**：`collect-step07-<layer>` 的 Release（part + checkpoint），与 03/04/05 完全隔离
**判据（accept）**：`failed_rate_max: 0.15`、`layers_min: 80`、`layers_max: 100`、`per_layer_rows_max: 5000000`
**证据**：report / releases / checkpoint / unit_errors / short_units

**新增的两项能力（只加在 07，不动老步骤）**
1. `exclude_done_tags`：选层时跳过已被 02/03/04/05 采过的层（按 Release tag 前缀查 checkpoint），避免重复采
2. 每批结束后自动记账 `state.steps.07.batches_done`，下一批 offset 自动 +100（大脑只需说"继续"）

## 2. STEP 08 —— 去重与真实地址数（纯报告，不采集）

**要解决什么**：现在 8,360 万行里，KS 采了 111 层叠加，覆盖率算出 415% —— 需要回答"**独立地址到底多少**"。

**数据源**：Release 里的 `part-*.tar.gz`（实测 steps 03/04/05 共 **687 个资产 / 1.4 GB**）
**算法**
1. 逐层流式下载 → 解压 → 只解析 `addr_key`（采集时已写好，`schema.py` 里 md5 前 16 位）
2. 州内用集合去重，跨层累计 `unique`；同时统计 `dup_rows = 总行 - unique`
3. 进程内存友好：按州分批，单州集合上限 500 万键（超了转 HyperLogLog 估算，误差 <1%）
4. 输出：每州「总行 / 独立地址 / 重复率 / 覆盖率（独立地址 ÷ Census 住房单元）」

**成本**：1.4 GB 流量，**8~12 job-分钟**（无上游请求，纯自家 Release）
**产物**：`collect/reports/DEDUP_REPORT.md` + `collect/dedup_status.json`
**判据**：`states_min: 40`、`dup_rate_max: 0.9`（只防异常，不做质量断言）、`unique_rows_min: 30000000`

## 3. STEP 09 —— 增量（只拉变更）

**要解决什么**：季度漂移监测。全量重采要 800+ 分钟，增量只需几分钟。

**机制**
1. 探测每层的编辑时间字段（`last_edited_date` / `EditDate` / `LASTUPDATE` / `last_edit`），取第一个存在的
2. `where = 字段 > since`（since 由上次成功增量时间决定，写进 `collect/delta_state.json`）
3. 增量产物打 **独立 tag**：`collect-delta-<layer>-<YYYYMMDD>`，**绝不覆盖**全量 tag
4. 无编辑时间字段的层 → 记 `no_delta_field`，不报错（这类层只能全量重跑）

**口径**：`select.source: "collected"`（只对已采过的层做），`since_days: 90` 默认
**成本**：待实测，预估 **<100 job-分钟**（取决于变更量）
**判据**：`failed_rate_max: 0.2`、`coverage_min: 0.7`（能探测到时间字段的层占比）
**证据**：report / releases(delta tag) / unit_errors
