# 自研模式 v2（SELF-DRIVE v2）

> 制定：2026-10-23（在 STEP02 折腾 14 小时、连撞三次同一面墙之后）
> 取代：`collect/SELF_DRIVE.md` 第 5/6 条（工头判定）与第 8 条（三振出局）
> 定位：这是**施工图**，不是理念文。改代码时照它改，不照 v1 改。

---

## 0. 一句话

**工人只管干，工头只管看；工人一停手，工头就叫大脑。
大脑核验、判断、改脚本、点火、然后去休息。
同一个问题卡两次 → 记档跳过 → 全流程跑通 → 叫老板一起收尾。**

---

## 1. 三个角色（职责边界，不允许越界）

| 角色 | 实体 | 只做这些 | **绝不做这些** |
|---|---|---|---|
| **工人** | `collect/run_step_0X.py` | 按死规则执行：取数、落盘、传 Release、写自己的 `_manifest.json` | 不做判断、不做重试决策、不写账本、不发通知 |
| **工头** | `collect/supervisor.py` | ① 看当前步有没有活着的 run ② 没有 → 叫醒大脑 ③ 记事实到账本 | **不做验收判定、不判原因、不重试、不收摊、不推企微** |
| **大脑** | pi（我） | ① 被叫来核验 ② 判断合格/不合格 ③ 不合格就查原因 ④ 改脚本 ⑤ 合格就按 ROADMAP 进下一步 ⑥ **每完成一步推企微汇报老板** | 不做没有证据的猜测、不在没核验的情况下宣称完成 |

**核心原则：脚本只会算出「1+1=2」，问它「1+2」它必然不知道。
所以「为什么失败」永远不许交给脚本 —— 那是知识储备的活，只有大脑能干。**

## 3. 材料由谁准备（关键：**不是工头带，是我预先写死**）

**先想清楚一件事**：工头是大脑造的。它对大脑说的每一句话，都是大脑当年写进它里面的。
所以「工头带的东西不够」= 大脑造工头时没想清楚，不是工头的错。

工头启动时只读三份文件，复述其中固定字段：

| 文件 | 作用 | 谁写 |
|---|---|---|
| `collect/ROADMAP.md` | 总目标 + 每步的验收判据 | 大脑（一次性） |
| `collect/steps/STEP-0X.md` | 本步：目标 / 输入 / 产出路径 / 验收判据 / **常见失败形态对照** | 大脑（每步开工前） |
| `collect/state.json` | 事实账本（当前步、最后 run id、产物位置、blocked 清单） | 工头只追加事实字段 |

**`STEP-0X.md` 必须包含的 5 个字段（缺一不可）：**

```markdown
## 目标
这一句话说明本步要达成什么

## 输入
上一步的产物在哪（tag / 路径 / 文件名规则）

## 产出
产物落在哪（Release tag、文件名、预期行数或文件数）

## 验收判据（大脑执行，脚本不执行）
- 必须：<可机械核对的数字/存在性>
- 必须：<第二条>
- 参考：<不是硬性但要看一眼的>

## 常见失败形态对照（大脑定位用，工头照抄进 Issue）
| 症状 | 大概率原因 | 先查什么 |
|---|---|---|
| err 非空 / 5xx / timeout | 环境类：上游抖动、限流 | 重跑即可 |
| 0 行且 err 为空 | 静默失败：参数无效、字段名错 | 看 HTTP 状态码与 error.message |
| 行数明显少于预期 | 分页/上限截断（maxRecordCount、Pagination not supported） | 看服务端 capabilities |
| 报错 Invalid URL / not started | 上游服务下线 | 搜替代服务，记 blocked |
| 数字不达标但无报错 | 逻辑错误：判定条件写错 | 对照上游 count 反推 |
```

## 4. 失败分型：脚本只落证据，分类是大脑的事

脚本**不判断**「这是哪类失败」，它只把原始证据写进 `_manifest.json`：

```json
{"id": "san_juan", "rows": 2000, "count": 22680, "diff": 0.9118,
 "err": "", "http_status": 400, "err_message": "Invalid or missing input parameter",
 "elapsed": 12.3}
```

分类由大脑做，三类：

| 类型 | 判据 | 大脑的动作 |
|---|---|---|
| `transient`（环境） | err 非空且是 5xx/timeout/限流 | 直接重跑，不改代码 |
| `logic`（逻辑） | 0 行但 err 空、400 参数错、行数偏差大 | 必须改代码 |
| `upstream`（上游缺失） | Invalid URL、Service not started、接口下线 | 找替代；找不到 → 记 blocked 跳过 |

## 5. blocked 机制（两次不解决就跳过，不堵流程）

**规则：同一个问题第 2 次出现且仍未解决 → 记档 → 跳过 → 继续下一步。**

写入 `collect/blocked.json`：

```json
[{
  "step": "02",
  "layer": "de_suss",
  "symptom": "0 行，err 空",
  "root_cause_hypothesis": "原 URL 返回 Invalid URL（400），Delaware SUSS 服务已下线",
  "evidence": ["get_json 返回 {'error': {'code':400,'message':'Invalid URL'}}",
                "ArcGIS 搜索无 Delaware 州 SUSS 替代服务"],
  "attempts": ["2026-10-23 第3次 pilot", "2026-10-23 第4次 pilot"],
  "impact": "DE 层缺 184,716 行；不影响其他 7 层",
  "status": "skipped",
  "decision_pending": "换源 / 用 NAD DE 顶 / 砍掉这一层 → 待老板定"
}]
```

**为什么跳过而不是停下来问**：
- 阻塞式设计会让整条流水线停在一个点上，后面所有步骤都看不到
- 后面的步骤跑起来经常反过来提供线索（今天就是：不纠结 de_suss，才发现了 nysam 有替代服务）
- **流程完整性 > 单点完美**

**全流程走完后**：大脑被叫醒 → 汇总 blocked 清单 → 推企微给老板 → 一起商量怎么补。

## 6. 通知通道：必须分开，不许混

| 通道 | 用途 | 谁发 | 到哪 |
|---|---|---|---|
| **内部唤醒** | 叫醒大脑 | 工头 | 哨兵队列 `/root/pi-work/sentinel/q.py` + 本机 todo，**不进任何对话窗口** |
| **企微汇报** | 向老板报进度 | **大脑** | 企微，只在「一步跑完/需要决策」时发 |

**铁律：工头不碰企微。** 老板收到的所有企微消息都应该是大脑在说话，不是机器在说话。

**双闹钟**（工头本身的可靠性）：
- GitHub Actions cron `*/10`
- 本机 cron `*/15`（`ops/patrol_kick.sh`，已装）
- 任一响就算叫到；两个都坏 = 整条链静默死，属于最高级别故障

## 7. 账本：只记事实，不记判断

`collect/state.json` 结构（v2）：

```json
{
  "project": "...",
  "current_step": "02",
  "mode": "self-drive-v2",
  "budget": {"minutes_used": 600, "minutes_cap": 1800},

  "last_run": {"step": "02", "run_id": 40024675586, "at": "...", "script": "run_step_02.py"},

  "awaiting_brain": true,          // 工头置 true；大脑处理完置 false
  "brain_review": {                // 只有大脑能写
    "at": "...", "verdict": "pass|fail",
    "note": "8 层中 7 层有数据，de_suss 上游下线已记 blocked"
  },

  "steps": {"01": {"status": "done", "at": "..."}, "02": {"status": "in_review"}},

  "blocked_count": 1
}
```

**删除的字段（从 v1 移除）**：
- `fail_streak` —— 「失败次数」是判断，不是事实
- `collapsed` —— 「收摊」是决定，不是事实
- `collapsed_reason` —— 同上

**新增**：`blocked.json` 单独一个文件，不塞进 state.json，便于人工翻阅。

## 10. 禁忌清单（今天踩过的，全部升级为硬规则）

1. **禁止 `|| true` 静默吞错** —— 今天 `git push || true` 让报告消失，工头读旧账误判
2. **禁止让脚本判「合格/不合格」** —— 它只会比数字，不会判原因
3. **禁止工头推企微** —— 叫醒大脑走队列，汇报老板走大脑
4. **禁止用单一数字判空壳** —— `<2KB` 不等于坏（一仓 3 个 OA 小文件是真实小数据集）
5. **禁止用会混入外部数据的 count 判「有没有数据」** —— 一仓 NAD 的 `returnCountOnly` 会混邻州点，实测 NH 35 万点全是外州
6. **禁止 push 不重试** —— 任何 `git push` 都要 fetch+rebase+retry，失败必须显式 `exit 1`
7. **禁止一次改多处后不验证就跑全量** —— 先小样本（1~2 个单元）验证，再放量
8. **禁止在收摊/跳过时不留证据** —— 跳过的必须有 `blocked.json` 记录，否则等于假装没发生过

## 11. 自检：v2 是否成立（5 个问题）

任何一步走不通时，用这 5 问自查：

1. **工头有没有越界做判断？**（它只该看「有没有活 run」）
2. **我给工头预先写的内容够不够？**（够的话我一被叫就能动手，不用再翻日志找线索）
3. **失败的原始证据有没有落盘？**（HTTP 状态码、error.message、count vs rows）
4. **这个失败是第几次？**（第 2 次就该记 blocked 跳过，不该再改第三次）
5. **我有没有在完成后推企微？**（老板不该靠猜来知道进度）

## 12. 附：2026-10-23 四个事故复盘（v2 的由来）

| 事故 | 表面现象 | 真实原因 | v2 怎么防 |
|---|---|---|---|
| 报告丢失、工头读旧账 | 判定「未通过」，但实际 6/8 层有数据 | `git push \|\| true` 静默失败 | 禁忌 1 + 禁忌 6 |
| 3.5 小时静默停摆 | 工头 cron 丢事件，没人点火 | 单闹钟 + 无兜底 | 双闹钟（§6） |
| san_juan 三次都只有 2000 行 | 判据说「误差 0.9118」但不合格 | 主键叫 `FID` 不是 `OBJECTID`，脚本不会说这个 | §1 脚本不判原因 + §3 常见失败对照 |
| de_suss 三次都是 0 行 | 每次重跑都一样 | 上游 URL 失效（Invalid URL） | §5 blocked 机制，第 2 次就跳过 |

**核心教训一句话**：**机器判断 + 机器重试 = 三次白跑。机器执行 + 大脑判断 = 每轮都前进。**
