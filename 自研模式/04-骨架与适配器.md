# L1 骨架与 L2 适配器

> L1 = 复制即得，零改动。L2 = 每个任务族一份，**新任务唯一允许写新代码的地方**。

---

## 一、L1 骨架目录约定

```
<repo>/
├── MISSION.md                 # D0 产物：目标 / 红线 / 预算 / 可跳过边界
├── policy.json                # 阈值与预算（运行期只读）
├── steps.json                 # 步骤配置：单一入口，改一处同步全部工人
├── step_docs/
│   └── STEP-0X.md             # D1 产物：五段契约
├── workers/
│   └── run_step_0X.py         # 工人：死脚本，只执行 + 落证据
├── supervisor/
│   └── supervisor.py          # 工头：只看活着/在动，叫大脑，记事实
├── mailbox/                   # 统一信箱（队列 + 分级 + 幂等 + 退信）
│   ├── envelope.schema.json
│   └── consume.py             # 串行消费：一次一条，BUSY 即排队
├── ledger/
│   └── events.ndjson          # append-only 事件流（唯一真相）
├── blocked/
│   └── <id>.json              # 跳过档案（含状态机）
├── reports/
│   └── <step>/manifest.json   # 四件套报告
├── tools/
│   ├── lint_pipeline.py
│   ├── verify_from_evidence.py
│   └── selftest.py
└── adapters/
    └── <task_family>.py       # L2：唯一允许改的文件
```

---

## 二、L1 各部件职责（越界即违规）

| 部件 | 只做 | 绝不做 |
|---|---|---|
| `workers/*` | 按步骤契约执行、写 manifest、追加账本事件 | 判合格、决定重试、发通知 |
| `supervisor.py` | 判存活 + 判在动、投信封、记事实 | 判验收、判原因、重试、推人看的通道 |
| `mailbox/consume.py` | 串行取一条、唤醒大脑、等结论、写回 | 并行处理、批量合并 P0/P1 |
| `ledger/` | 追加、拒绝覆盖 | 提供「当前状态」作为唯一真相（应为派生） |
| `tools/lint_pipeline.py` | 报告违规 | 自动修改代码 |
| `tools/verify_from_evidence.py` | 只读证据重算、比对账本 | 修改账本 |

> **工头的两个判据缺一不可**：进程存活 **且** 心跳产出在动。只看存活 = 把「假活」当健康。

## 三、L2 适配器接口（每个任务族实现这四个函数）

```python
# adapters/<task_family>.py

def enumerate_units(ctx) -> list[Unit]:
    """枚举任务单元（层 / 页 / 分片 / 文件）。"""

def fetch(unit, ctx) -> Artifact:
    """取单个单元，落盘到约定路径，返回证据指针。"""

def verify(unit, artifact, ctx) -> dict:
    """按 STEP 判据判定，返回 manifest 四件套。
    只算，不判「合格/不合格」——返回数字，判定归大脑。"""

def plan_shards(units, budget, measured_rate) -> list[Shard]:
    """按实测速率反算分片：单 job 时限 × 速率 × 60%。"""
```

**约束**：
- `verify` 返回**数字与布尔**，不返回「是否通过」的终判
- 适配器里不许出现推送给人的通道
- 适配器改动必须留 `script_sha`，进账本
- 适配器是**唯一**允许新增依赖的地方

## 四、最小可跑集（MVP，用于 D3 干跑）

只需 7 个文件就能跑通全链路：

1. `MISSION.md`
2. `step_docs/STEP-01.md`
3. `workers/run_step_01.py`
4. `supervisor/supervisor.py`
5. `mailbox/consume.py`
6. `ledger/events.ndjson`（空文件）
7. `adapters/<family>.py`

**判据**：这 7 个文件能把 D3 的四条放行闸门全部跑出来，一个不多。加文件必须有理由。

## 五、跨仓库复用的两种形态

| 形态 | 做法 | 适用 |
|---|---|---|
| **复制** | 直接复制 L1 目录到新仓 | 简单、可控、各仓独立演进 |
| **引用** | 独立母体仓 + 各业务仓 submodule / 脚本拉取 | 骨架需统一升级时 |

**建议**：先复制。等连续 3 个仓都验证过同一份骨架，再考虑引用 —— 否则母线一改全线崩。

## 六、多仓库并行时的信箱纪律

- **一个信箱服务，N 个仓库**。任何仓库的工头都往同一个信箱投，不许直连大脑
- 信封必须带 `repo_full_name + repo_url + workflow_name + run_id`，否则大脑无法定位
- 信箱全局并发 = 1：一次只唤醒大脑处理一条
- P0 插队到剩余 P1 之前，**但不抢占手上这一条**
- 每仓限流 + 每仓一把签名 key（签名机制在 L1 实现时必须落地）
