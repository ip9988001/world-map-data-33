## 1. 事故：`--force-layers` 从来没有真正重采过

run `45010130014`（2026-11-22 09:58Z，点名 force 重采 4 层）的实测：

| 现象 | 数值 |
|---|---|
| 4 层里 3 层的 `elapsed_s` | **1.9 / 2.1 / 3.0 秒** |
| 这 3 层的新采行数 | **0**（shard 日志原文：「本次续跑：跳过 N 个已完成单元，新采 0 行」） |
| 账本 `rows` | 直接取上轮包 → `cgis911` 163,221/81,784、`qKAFwdGU` 363,000/181,471 **原样保留** |

链路真相：

```
collect-full.yml  force_layers ─┬→ full_plan.py   --force-layers  ← 只绕「层级 skip_done」+ 提到队首
                               └→ full_shard.py  --force-layers  ← done_layers 判完成也照样跑
                                        └→ run_step_05.py --layer <id>
                                                └→ pilot.collect_arcgis_v2()
                                                     ├─ _load_ckpt(plan_hash) / _fetch_ckpt_asset()  ← ★ 仍续跑
                                                     └─ done = 检查点里的 done_units → todo = [] → 一行不采
```

`PILOT_FORCE_RERUN=1`（`full_shard.run_layer(force_rerun=True)`）只做两件事：**备份**旧检查点、
收尾时**按单元合并**。它不改「续跑」这件事本身 —— 所以 elapsed 2 秒、新采 0 行是必然结果。

**更重的连锁**：W33-060 的 supersede 逻辑在 `ckpt_guard.merge_checkpoints()` 里，
而合并只在「旧检查点与新切分不一致」时才会被调用。不重采 → 不合并 → **supersede 永不触发** →
2× 的 100 层再跑一百轮也不会归位。

## 2. 开关：`force_fresh`（workflow 输入 `force_fresh=1`）

语义只加一层，**不动既有语义**：

| 传参 | 名单内的层 | 名单外的层 |
|---|---|---|
| `force_layers=A` | 提队首 + **仍 checkpoint 续跑**（现状，一个字不变） | 不受影响 |
| `force_layers=A` + `force_fresh=1` | 提队首 + **忽略检查点真重采**（新代际） | 不受影响（续跑行为照旧） |
| 只传 `force_fresh=1` | 什么都不发生（`::warning::` 喊出来） | 不受影响 |

### 传透链路（plan → shard → pilot）

| 跳 | 位置 | 行为 |

| ② plan | `collect/full_plan.py:322` `--force-fresh` → `:483` `plan.force_fresh` / `plan.force_fresh_layers` | 只把**意图**写进 plan（供 shard 与事后审计），不自己决定分层 |

## 3. `supersede_all`：切分粒度变了也必须整代 supersede

W33-060 的规则是「新代际重采了**同一个 unit 索引** → 旧包 supersede」。实测 `qKAFwdGU`
暴露了它的第二个洞：

```
旧检查点 unit_rows      = {0: 90,736, 1: 90,735}          ← 本代，r33297e41- 前缀 2 包
旧检查点 units_legacy   = {u00000: 90,765, u00001: 90,764}  ← 上一代，无前缀 2 包
旧检查点 rows_total     = 363,000
新代际（UNIT_ROWS 变化的另一种切法）= 1 个单元
```

新代际只有 `idx=0`：按索引对齐会把旧 `u00001`（90,764）当「新代际没有这个索引 → 唯一副本」照计
→ `rows_total = 181,471 + 90,764 + 90,735 = 362,970`，还是双算。

所以 fresh 在**整层采完**（全部单元 done + 上传成功）时改成 `supersede_all=True`：
旧代际**全部**落 `superseded_by`、`counted_rows=0`。判据留给调用方
（`pilot.py:1703` `set(range(len(units))) <= done_units`），因为只有它知道「这层是不是整层重采完了」。

新代际某个单元没采成功时**不整代 supersede**：那个索引的旧包继续计入（唯一副本），不拿「fresh」当丢数据的理由。

## 4. 账本口径：fresh 记录是权威值

`ledger_merge.pick_better()` 原来是「状态优先，同状态取行数大者」。对 fresh 重采这是错的 ——
旧账本那一坨**大数**正是双算，让「大者赢」等于让错的那个数永远赢。
现在 `new.fresh=True` 且状态不更差 → 取 `new`（`fresh_rerun_authoritative`）。

`rows` 因此变小是**预期**的（363,000 → 181,471），所以层记录同时带：

```json
{"fresh": true, "rows_before_fresh": 181471, "rows_before_fresh_total": 363000,
 "rows_superseded_by_fresh": 363000, "supersede_mode": "fresh_all",
 "regression_reason": "fresh 真重采：旧代际标 superseded_by、不计入 rows_total…",
 "row_regression_evidence": "collect/ledger/05b_run<RUNID>.json"}
```

`ckpt_guard.guard_ledger_rows` 认这个证据路径（`step_full_report` **先写 run 账本再跑闸门**，
所以这个文件在判定时一定在），于是「行数变小」被**放行并留痕**（`revisions[kind=row_regression_allowed]`），
而不是被拒写。

## 5. 反例（用户点名要的）

`force + fresh` 但上游一行没给 → 层记录必须写 `fresh_but_upstream_empty: true`，
`reason` 里写「旧代际**未** supersede，不当作重采成功」，状态仍是 `failed`。

实现：`full_shard.run_layer()` 末尾（`if fresh and rows == 0`）。**不许静默** —— 静默的后果是
「账本看着像重采过了，2× 原样躺着」。

### 本机实采对照（真上游 `qKAFwdGU`，上传打桩、一行不写远端）

| | rows | count | 新采包 | 新采行 | elapsed | 检查点 rows_total |

| A. force+resume（默认） | 363,000 | 181,471 | 0 | **0** | **1.8s** | 363,000（原样） |

B 的合并报告：

```json
{"rows_before_fresh": 181471, "rows_before_fresh_total": 363000,
```

## 7. 怎么用（派单）

```bash
gh workflow run collect-full.yml --repo ip9988001/world-map-data-33 \
  -f stage=05b -f size=0 -f workers=4 \
  -f force_layers="<层1>,<层2>" -f force_fresh=1
```

- **派单前先过 `docs/PREFLIGHT-GATE.md`**（D9/D10/D15 与在跑 run 的层交集必须为空）。
- 名单外层的续跑行为不变 → 这次派单只会重采名单内那几层，不会把全量拉一遍。
- `force_fresh` 不传 = 老语义（提队首、仍续跑），在跑的用法不受影响。
