# 宗地几何落盘方案 · 三档成本实测（2026-10-30）

> 一句话结论：**推荐第 ② 档 —— 存 6 位小数（0.11 m）+ RDP 1e-5° 的简化 rings**。
> 代价：总量 5.03 GB → 6.74 GB（**+1.71 GB / +34%**），单资产最大 ~9 MB（离 GitHub 2 GB 上限远），
> 每层最多 18 个资产（离 1,000 上限远）。**存原始 rings** 只多 0.76 GB，但多出来的是
> 亚毫米级的投影噪声，买不到任何信息；**只存质心**便宜 1.0 GB，但丢掉边界，跨县宗地永远只能靠质心判县。
>
> 本轮**只出数、不动代码**：几何采集侧仍按 `PILOT_POLY_CENTROID`（默认开）只落质心；
> 1,038 个 `geom_missing` 层的补采方案见第五节，**排期在 04b/05b/07b/10b 全部结束之后**。

复现：`python3 analysis/parcel_rings_cost.py`（零网络；数字全落 `analysis/parcel-rings-cost.json`）

## 一、口径先说清楚（哪些是实测，哪些是假设）

| 量 | 值 | 来源 |
|---|---|---|
| 每顶点字节（全精度 double） | **39 B**（中位，p10 38 / p90 40） | 实测：本机 300,000 个真实坐标值（`dist/intake-full` 点层 lat/lon）json 序列化后的字符数 |
| 每顶点字节（6 位小数） | **23 B**（缩到全精度的 59%） | 同上，`round(x, 6)` 后再量；1e-6° ≈ 0.11 m |
| gzip 压缩率（全精度） | **0.217** | 实测：真实坐标值拼的宗地尺度环，20,000 顶点 |
| gzip 压缩率（6 位小数） | **0.255** | 同上（数字变短 → 熵变大，压缩率反而略差） |
| gzip 压缩率（本机真实县界环） | **0.27**（526,898 顶点） | 实测：`analysis/tiger_county/*.json.gz` |
| 环边长 | 中位 **0.00375°**（≈416 m）/ p10 0.00149° | 实测：523,839 条边 |
| RDP 1e-5° 顶点保留率 | **99.98%** | 实测：400 个真实环 / 104,815 顶点 |
| 宗地层行数 | **1,238 层 / 36,473,089 行** | `schema/field-map-v2.json` 的 `rows_total`，与 `collect/parcel_audit.json` 的在盘行数**逐层核对一致** |

**唯一没实测的量：每宗地几个顶点 v**（本机只有 `Shape__Length`/`Shape__Area`，没有 rings）。
所以下面三档都按 v = 5/8/12/24 给敏感性表 —— **结论在 v=5 就成立**，不依赖猜 v。
参考量级：矩形宗地 5 个顶点（含闭合点），带一处凹口 7 个，不规则宗地 10~20 个。

## 二、三档存储增量（36,473,089 行，GB 为十进制）

| v（顶点/宗地） | ③ 原始 rings 未压 | ③ 原始 rings 压缩 | ② 简化 rings 压缩 | ① 只存质心（一份 / 两份） |
|---|---|---|---|---|
| v=5 | 7.11 GB | 1.54 GB | 1.07 GB | 0.71 / 0.99 GB |
| **v=8（推荐取值）** | **11.38 GB** | **2.47 GB** | **1.71 GB** | **0.71 / 0.99 GB** |
| v=12 | 17.07 GB | 3.70 GB | 2.56 GB | 0.71 / 0.99 GB |
| v=24 | 34.14 GB | 7.40 GB | 5.12 GB | 0.71 / 0.99 GB |

- **①「一份」**：只把 `lat`/`lon` 填上（宗地层现在这两列是 null）；
  **「两份」**：再写一份同值的 `_lat`/`_lon`（NAD 口径并存）。
  实测（本机 20,000 行真实采集记录、坐标逐行不同）：`lat/lon` 为 null 时 **53.99 B/行**
  → 填 `lat/lon` **73.55 B/行（+19.56）** → 再存 `_lat/_lon` **81.02 B/行（+7.47）**。
  两份坐标只多 27% 而不是 100%，因为同一个数字紧挨着出现，gzip 压掉了大半。
- **②简化** = 6 位小数 + RDP 1e-5°。实测保留率 99.98%，所以这一档**实际就等于「只做小数位截断」**：
  1e-5° = 1.1 m 的容差对「直线边 + 真角点」的宗地删不掉任何顶点（边长中位 416 m，
  小于 1e-5° 的边占 0.00%），它真正能压的是**被加密的弧线**（有些县把圆弧打成 1 m 一个点）。
- **③原始** = ArcGIS 原样返回的全精度 double（`-97.12345678901234`）。比 ② 多 0.76 GB，
  买的精度是 1e-14°（亚微米级）—— 没有任何下游用途。

## 三、GitHub 上限判断：**不是瓶颈**

| 约束 | 上限 | ③ 原始 rings（v=8）最坏情况 | 结论 |
|---|---|---|---|
| 单个 Release 资产大小 | 2 GB | 一个「单元」= `unit_rows` 100,000 行 → **6.8 MB**（v=24 也就 20 MB） | 差 ~100 倍，永不触线 |
| 单个 Release 资产数 | 1,000 | 资产数 = ⌈层行数/100,000⌉；最大层 1,742,760 行 → **18 个** | 触线要单层 >1 亿行，没有这样的层 |
| 总量 | 软上限 | 5.03 GB → **7.50 GB**（+2.47） | 完全可行 |

**所以「存原始 rings 是否可行」的答案不是「技术上放不下」，而是「放得下但没必要」**：
真正的成本不在磁盘，在**下游每次全量重算都要重下 2.5 GB**，以及采集侧写盘 IO +49%。
不需要分卷、不需要外部存储 —— 网络这一层（GitHub）不构成任何阻碍。

## 四、推荐：② 简化 rings

**为什么是 ②**

1. **rings 本来就在响应里**：采集已经是 `returnGeometry=true`，我们只是把它**算完点就扔掉**。
   落盘的边际成本只有磁盘和 IO，**零额外上游请求** —— 这是唯一「免费」拿几何的时机。
2. **6 位小数足够**：1e-6° = 0.11 m，远小于任何县级宗地数据的精度（m 级）。
   全精度多花的 0.76 GB 买到的是投影运算的浮点尾数。
3. **1e-5° RDP 是免费保险**：实测保留 99.98%（直线边不动），只在加密弧线上真正省字节，
   不会误删角点。
4. **比「只存质心」多的 1.0 GB 换到的东西**：跨县宗地可以按**边界**判县（质心只能给一个点），
   将来做宗地级去重/邻接/边界复算不用重采（重采一次 = 3.3 万次上游请求 + 数小时，见第五节）。

**代价（必须写明白）**

| 代价 | 量化 |
|---|---|
| 存储 | 5.03 GB → **6.74 GB**（+1.71 GB / +34%），v=8 口径；v=24 时 +2.56 GB |
| 采集侧写盘 IO | part 体积 ≈ ×1.34（同样的行数，多写 rings） |
| 下游读取 | intake 逐层解压要多解 rings；建议 intake 只**跳过** rings 字段，不要为它建表 |
| 不可逆 | 6 位小数 + RDP 是有损的：要拿回原始精度只能重采 |
| 落地前提 | 需要改 `normalize()` 之外的落盘结构（记录里加 `rings` 字段）并让 intake 显式忽略它；**本轮不动** |

**如果连 1.0 GB 都不想花**：①档（只存质心）已经在跑（`PILOT_POLY_CENTROID` 默认开），
代价是跨县宗地只能用质心判县 —— 按 `COUNTY-ASSIGN` 的实测，质心落错县的比例极低（宗地跨县主要发生在
县界沿河道/山脊的不规则段），但不是 0。

**不建议**：③ 原始 rings（多付 0.76 GB 买亚微米噪声）；
也不建议走分卷/外部存储 —— 上限根本不是瓶颈，引入分卷只会增加下游拼装复杂度。

## 五、1,038 个 `geom_missing` 层的补采方案（**只出计划，本轮不派发任何批次**）

### 5.1 入口设计：`--centroid-only`

只补**质心**，不重取属性、不动已有数据资产：

```
python3 collect/pilot.py --layer <id> --centroid-only          # 单层直跑
python3 collect/centroid_backfill.py --plan collect/ledger/centroid_plan.json --concurrency 4
```

> 为什么不是 `--kick 10c`：`steps.json` 的步号文法只允许「基础步 0..NN」和「`<基础步>b`」
> （`supervisor.py --entry-check` 第 19 条），`10c` 会当场判红。补采几何是**一次性运维动作**，
> 不写进 steps.json 的步骤表，走独立入口 + 独立账本（`collect/ledger/centroid_plan.json`）。

强制语义（写进 argparse 就固化，不给调用者改的余地）：

| 参数 | 值 | 理由 |
|---|---|---|
| `outFields` | **只取主键**（`objectIdField`） | 属性已经在资产里，重取 = 白花流量 |
| `returnGeometry` | **false** | 只要质心，不要 rings；单页载荷从 ~1.2 KB/行降到 ~100 B/行 |
| `returnCentroid` | **true** | 服务端算质心，`outSR=4326` 直接是 WGS84 |
| `outSR` | `4326` | 与既有资产同口径，不做二次投影 |
| 落盘 | `collect/out/<layer>/centroid-<unit>.ndjson.gz`，行格式 `{oid, _lat, _lon, src_layer}` | **不写 part-*.ndjson.gz**，现有数据资产一个字节都不改 |
| 检查点 | `<tag>-centroid` 独立 tag + 独立 `plan_hash` | 与属性采集的检查点互不干扰，失败重跑不会污染原账本 |
| 合并 | 新增 `collect/geo_patch.py`：按 `oid` 把 `_lat/_lon` 回填进 `dist/intake-full` 的 addr/aux_parcel 表 | 只加两列，不重跑 intake |

铁律：**补采只增加坐标，不重写任何已有行**。任一层补采失败 → 该层保持 `geom_missing`，
下一轮再来，不阻塞其它层。

### 5.2 成本（全部按本地数据算，无一次上游调用）

| 项 | 值 | 依据 |
|---|---|---|
| 层数 | **1,038** | `schema/coord-salvage-v1.json` 里 `status=geom_missing` 的层 |
| 行数 | **31,412,190** | 同文件逐层 `rows` 求和 |
| 分页请求 | **30,454** 次 | 逐层 `⌈rows / min(layer_plan.pagesize, 2000)⌉`（pagesize 是当初实测的页大小，不是一律按 2000） |
| count 请求 | **1,038** 次 | 每层一次 `returnCountOnly`，用于对账（行数不齐要能发现） |
| 合计请求 | **33,066** 次（含 5% 重试冗余） | 30,454 + 1,038，×1.05 |
| 下行流量 | **≈3.1 GB** | 100 B/行 × 31.4M（`{"attributes":{"OBJECTID":…},"centroid":{"x":…,"y":…}}`） |
| 耗时（乐观） | **≈1–2 h**（4 层并行 × 4 线程） | 单页 ~1,031 行、~1 页/秒/线程 → ~1,031 行/秒/线程 |
| 耗时（保守） | **≈3.2 h**（4 层并行） | 按与「全属性采集同速」676 行/秒·job 反推：31.4M/676 = 775 job-分钟 |

耗时口径的两个锚点：intake 从 GitHub Release 下载+解析实测 **2,542 行/秒·进程**；
STEP-10 的验收预算 `budget_min_max ≤ 900 job-分钟` 反推全属性采集 ≈676 行/秒·job。
质心补采的单页载荷只有全属性的 ~1/12，落在两者之间偏乐观一侧。

### 5.3 排期闸门（**硬约束，写死在计划里**）

```
禁止派发条件（任一为真即不许开跑）：
  1. GitHub run 41019004076（collect-full / 04b）未结束
  2. 05b / 07b / 10b 任一补采阶段仍在跑（stage 未收尾）
  3. 本机 county T2 逐行判县（county_assign.py）仍在跑
理由：补采是**同一批 ArcGIS 服务**的并发增量，抢并发会把在跑的补采拖成 no_progress，
      而且 04b/05b/07b/10b 的 unit 重试逻辑对并发敏感（STEP-12 卡死阈值的教训）。
```

闸门通过后的执行顺序：
1. `--centroid-only` 先跑 **10 层灰度**（挑 rows 最大的 10 层），核对：请求数 / 行数 / 非空率 / 无 4xx；
2. 灰度对账全绿 → 按每批 40 层推进，批间核对 `centroid` 入账；
3. 全部完成后跑 `collect/geo_patch.py` 回填，再跑 `county_assign.py` 单层复核 5 层（判出县应与已有坐标层同量级）；
4. `schema/coord-salvage-v1.json` 里这 1,038 层的 `status` 由 `geom_missing` → `centroid_backfilled`。
