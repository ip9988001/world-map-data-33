## 2. P0 · 会让自研模式直接跑不起来（必须先修）

### P0-1 采集 step 缺 `GH_TOKEN`

**位置**：`.github/workflows/collect-pilot.yml` → `jobs.collect.steps[name=采集 …]`

**现状**：该 step 只有 `PILOT_HEARTBEAT_PUSH`、`PILOT_RELEASE_TAG`。
`pilot.py` 的 `_upload()` / `_publish_ckpt()` / `_fetch_ckpt_asset()` 全在调 `gh release …`。
Actions 的 shell step **不会自动注入** `GH_TOKEN`（`actions/checkout` 只给 git 塞 extraheader，与 `gh` 无关）。

**后果**：所有单元上传失败 → 数据全留本地 → 断点续传形同虚设 → 磁盘涨满。

**改法**：

```yaml
      - name: 采集 ${{ matrix.layer }}（单元级断点续传）
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}          # ★ 新增
          PILOT_HEARTBEAT_PUSH: "1"
          PILOT_RELEASE_TAG: collect-pilot-${{ matrix.layer }}
```

**验证**：灰度 san_juan 后日志出现 `↑ 已发布 san_juan-u00000.tar.gz`；
`gh release view collect-pilot-san_juan --json assets` 能列出资产。

### P0-2 单元「完成」判据错误（最危险）

**位置**：`collect/pilot.py` → `one()` / `_unit_range()` / `_unit_ids()`

**现状**：`one()` 里 `_record_unit(ck, i, rows, files)` **无条件**执行，
不管有没有 `err`、不管上传成不成功都进 `done_units`。

**三个后果**：
1. 单元内 `query_fail`（429/5xx 重试耗尽）→ 带空洞标 done → 续跑跳过 → **缺口永久固化**
2. 采集成功但上传失败 → 标 done；换一个 run（新 runner）本地文件已不存在 → 该单元被当「已完成」跳过 → **数据永久丢失，账本显示 100%**
3. 服务静默返回空页（rows=0、err 空）→ 同样标 done

**改法**：三条同时成立才算完成 —— `err 为空` 且 `rows ≈ expect` 且 `上传成功`。

1）两个单元函数多返回一个 `expect`：

```text
def _unit_range(api, oid_field, defexpr, lo, hi, idx, ps, limit, log, prog, lock, ck):
    ... # 函数体完全不变
    return rows, files, err, expect          # ← 只改返回值：多带 expect（本区间 count）

def _unit_ids(api, batches, idx, log, prog, lock, limit):   # ← 多收一个 limit（配合 P1-3）
    ... # 函数体不变
    return rows, files, errs, sum(len(b[1]) for b in batches)
```

2）`one()` 重写：

```python
    def one(i, u):
        if STRATEGY == "ids":
            rows, files, err, expect = _unit_ids(api, u, i, log, prog, lock, limit)
        else:
            lo, hi = u
            rows, files, err, expect = _unit_range(api, oid_field, defexpr, lo, hi,
                                                   i, ps, limit, log, prog, lock, ck)
        # ① 无错 ② 行数对得上（容差 0.1%，但 --limit 试采时不判）③ 上传成功
        if not err and not limit and expect > 0 and rows < expect * 0.999:
            err = "short:%d/%d" % (rows, expect)
        ok = False
        if files and not err:
            with up_lock:
                ok = _upload(files, log)
        done_ok = (not err) and (ok or not files)      # 空单元无需上传
        with lock:
            ck.setdefault("unit_uploaded", {})[str(i)] = bool(ok)
            if done_ok:
                _record_unit(ck, i, rows, files)
                ck.setdefault("unit_errors", {}).pop(str(i), None)
            else:
                ck.setdefault("unit_errors", {})[str(i)] = (err or "upload_failed")[:200]
            _save_ckpt(ck)
            snap = json.loads(json.dumps(ck))
            if done_ok:
                _purge(files)                          # 只有真完成才删本地
        if done_ok:
            _publish_ckpt(snap, log)                   # 挪到锁外（见 P2-5）
        return rows, (err or "")
```

**⚠ 两个已知取舍（核查时发现，已在上面代码里处理）**：
1. `--limit` 试采会让 `rows < expect` 永远成立 → 判据里加 `not limit` 排除，否则 CI smoke 必红。
2. 「上游删了几条 ID」的层会永远 `short` → 在 `with lock:` 里加一段确认逻辑（已仿真验证）：

```python
            # 同一单元连续两次 short 且行数一致 → 认可「上游真实就这么多」，不是失败
            if err.startswith("short:"):
                st = ck.setdefault("unit_short_tries", {}).setdefault(str(i), {"n": 0, "rows": -1})
                if st["rows"] == rows:
                    st["n"] += 1
                else:
                    st["rows"], st["n"] = rows, 1
                if st["n"] >= 2:
                    ck.setdefault("unit_short_ack", {})[str(i)] = rows
                    err = ""            # 转成 done，但证据留在 unit_short_ack
```

  `unit_short_tries` 跟 `ck` 一起进检查点，所以「两次」可以跨 run 累计。`unit_short_ack` 最终会写进
  manifest 的 `short_units`，让大脑判验收时一眼看到「哪层少了几行、原因是什么」。

**验证**：mock 增加「上传返回 False」用例，断言 `done_units` 为空、`unit_errors` 有值、重跑能补齐。

### P0-3 兜底上传判据看错字段

**位置**：`.github/workflows/collect-pilot.yml` → 兜底 step

**现状**：判据是「`done_units` 非空 → 认为 pilot 已发布」。
但 `done_units` ≠ 发布成功（P0-2 第二个后果）→ 上传全失败时**兜底主动跳过 → 数据全丢**。

**改法**（必须单行，YAML 缩进一错整份 workflow 就废）：

```bash
          N=$(python3 -c "import json,os;p='collect/out/%s/_checkpoint.json'%os.environ['ID'];print(sum(1 for v in json.load(open(p)).get('unit_uploaded',{}).values() if v) if os.path.exists(p) else 0)")
          if [ "${N:-0}" -gt 0 ]; then echo "✅ pilot 已成功发布 ${N} 个单元到 $TAG"; exit 0; fi
```

**验证**（已实测，见 §4）：`unit_uploaded` 全 false → N=0 走兜底；有 true → N=2 跳过。

## 6.5 消费者怎么取数（断点续传后的产物形态）

单元化之后，一个层的交付物是 **tag 下的一串资产**，不再是一个整包：

```bash
tag=collect-pilot-nysam
gh release download "$tag" -p 'nysam-u*.tar.gz' -D /tmp/nysam      # 所有单元
gh release download "$tag" -p 'nysam-checkpoint.json' -D /tmp/nysam  # 索引（有哪些单元、各多少行）
tar czf nysam.tar.gz -C /tmp/nysam .                                # 需要整包时自己拼
```

`checkpoint.json` 里的 `unit_rows` 就是逐单元行数账本，`sum(unit_rows.values()) == count` 即完整。
**谁要整包，谁按这个规则拼**——worker 不再负责拼整包（否则又回到「一崩全丢」）。

## 7. 明确不修（避免过度设计）

| 项 | 理由 |
|---|---|
| 单元内部断点（跑到 80% 崩） | 单元≈50 万行≈8 分钟，重采可接受；再细化会让资产数量与元数据复杂度翻倍 |
| 自动清理历史 Release | STEP04/05 前先定命名规范，清理动作人工确认 |
| 工头推企微 | v2 铁律：老板只该收到大脑的话 |
| 每单元先 `gh release view` 再上传（省一次失败调用） | 只是噪音，不是错误；等真有速率问题再优化 |
| `collect-batch.yml` 的 `d[:40]` 截断（一次 run 最多 40 层，`count` 也只反映截断后的数） | 不是 bug，是分页设计；但工头看 `count=40` 会误判，已在 P2-2 自检里加一条提示 |
