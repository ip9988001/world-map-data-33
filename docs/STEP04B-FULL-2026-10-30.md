### 7.1 现象

run `41092912755`（04b 续跑，`ref=feat/gold-intake`，headSha `48d1a48`）总结论 **completed / cancelled**：

| job | 结论 | 结束时刻 | 说明 |

| merge | failure | 19:18 | 账本**生成了但没落地**，随后闸门步 `KeyError: 'STAGE'` |

### 7.2 根因（三条，全是脚本/工作流 bug，不是采集失败）

1. **假红（shard 4/5/7/8）**：采集在 runner 工作区留下未提交产物（`collect/progress/*.json` 等），提交步执行的是
   裸 `git checkout -q -B main origin/main`（无 `-f`）→ Git 拒绝并退出：

   ```
   error: Your local changes to the following files would be overwritten by checkout:
       collect/progress/s_rest_services_msdi_structures_addresses_map_v1_MapServer_0.json
   ```

   `set -e` 下整步退 1 → 整片判红。四片同一原因（17:02 / 17:11 / 18:05 / 18:06 各一次）。
2. **账本没落地（merge）**：merge 的提交步用 `git fetch + git rebase origin/main`，工作区同样被 artifact 落下的片账本/产物污染
   → `cannot rebase: You have unstaged changes`（被 `2>/dev/null` 吞掉）→ 6 次重试**重复同一个错误** →
   只打 `::warning::账本推送失败` 就继续 → `collect/04b_ledger.json` 一行没上 main。
3. **merge 判红（闸门步）**：闸门脚本读 `os.environ["STAGE"]`，而 `STAGE` 只在 shell 里赋值、**没有导出/没在 `env:` 注入** →
   `KeyError: 'STAGE'` → merge 整体 failure。所以「merge failure」**不是**「deps 被 cancel 就会失败」那种连锁。

### 7.3 为什么数据一行没丢

- 每层的 `-uNNNNN.tar.gz` 早就在采集过程中推到了 Release（`tag=collect-step04b-<layer>`），不依赖 runner 本地；
- 每片账本 `led-04b-N` 用 `if: always()` 上传 artifact，本次 5 片（2/4/5/7/8）全部在；
- merge 也确实成功生成了汇总账（日志 19:17:13 打印 `layers_n 20 / ok 14 / empty 1 / failed 5 / rows 12,640,072`），
  与本次本地复原的数字**完全一致** —— 丢的是「提交/推送」这一步，不是数据。

### 7.4 merge 到底会不会因 shard 红而漏账（基于 artifact 实证）

| 环节 | 实际发生 | 结论 |
|---|---|---|
| `needs: [plan, shard]` + `if: always()` | shard 有 failure/cancelled 时 merge 仍启动 | 不会因 shard 红而跳过 merge |
| artifact `led-04b-*` | 5 片全在，merge 全下到了 | 账本来源完整 |
| 汇总脚本 | 成功生成 `collect/04b_ledger.json` | 生成本身没问题 |
| 提交/推送 | 6 次全败（根因 2） | **漏的是落地，不是生成** |
| 文档上传 artifact | glob 是 `docs/STEP0*-FULL-*.md`，实际文件名 `docs/04B-FULL-2026-10-30.md` 不匹配 | 文档连 artifact 都没留下（本次已统一命名 `STEP04B-FULL-<date>.md`） |

→ 结论：**本次漏账是「提交步 + 文件名 glob」两个 bug 造成的，不是 merge 依赖逻辑的问题**。
修复后 merge 在「有片被 cancel / 有片假红」时都能把部分账本推到 main；闸门只负责「不许接续 05b」。
